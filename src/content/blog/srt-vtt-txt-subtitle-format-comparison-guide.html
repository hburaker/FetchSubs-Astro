Short answer: download SRT if the captions are going into a video editor or a desktop player, VTT if they are going onto a web page with an HTML5 <video> element, and TXT if you only want the words. All three contain the same text. What changes is whether the timing is kept and how it is written down.

To make the differences concrete, every sample below is the real output FetchSubs produces for the English captions of Me at the zoo, the 19-second clip that was the first video uploaded to YouTube. The file names it gives you are Me_at_the_zoo_en.srt, Me_at_the_zoo_en.vtt and Me_at_the_zoo_en.txt; an auto-generated track gets _auto added before the extension, so you can tell them apart later.

SRT: the one almost everything accepts

SRT (SubRip) is about as simple as a subtitle format can be. Each caption is a block: a counter, a timing line, one or more lines of text, then a blank line.

1
00:00:01,200 --> 00:00:03,360
All right, so here we are, in front of the
elephants

2
00:00:05,318 --> 00:00:07,974
the cool thing about these guys is that they
have really...

The detail that trips people up is the comma before the milliseconds: 00:00:01,200, not 00:00:01.200. Hours are always written, even for a 19-second video. There is no header, no styling and no positioning in the basic format, which is exactly why support is so broad.

SRT is what I'd pick for anything that isn't a web page. Desktop players such as VLC load it, video editors such as DaVinci Resolve and Premiere Pro import it, and YouTube Studio accepts it when you upload captions to your own video (SubRip is on YouTube's list of supported caption files). If you want a player to load the file without asking, give it the same base name as the video and keep both in one folder: lecture.mp4 next to lecture.srt.

The YouTube to SRT page has more on this format, and the video editor's guide covers importing SRT into Resolve and Premiere.

VTT: the format browsers actually play

WebVTT is the caption format of the web. The <track> element in HTML expects WebVTT, so if you want captions on a video you host yourself, this is the file you need. It looks a lot like SRT, with a few differences:

WEBVTT

1
00:00:01.200 --> 00:00:03.360
All right, so here we are, in front of the
elephants

2
00:00:05.318 --> 00:00:07.974
the cool thing about these guys is that they
have really...
  • The file has to start with WEBVTT, followed by a blank line before the first cue.
  • Milliseconds come after a dot, not a comma.
  • The hours part is optional, so 00:01.200 is valid too. FetchSubs always writes the hours, which is also valid.
  • The number above each cue is an optional cue identifier. FetchSubs keeps the counter there so the VTT and SRT files line up block for block; players simply ignore it.

VTT can also do things SRT can't. A timing line can carry cue settings (line, position, size, align and vertical) to move a caption, for example out of the way of on-screen text. Your page's CSS can style the captions through the ::cue pseudo-element, and the file itself can hold NOTE comments and STYLE blocks. MDN's WebVTT format reference lists the rules, including one worth knowing if you edit cues by hand: a blank line ends a cue, so the caption text itself can't contain an empty line.

Hooking a VTT file up to a video takes one line inside the <video> element:

<track src="Me_at_the_zoo_en.vtt" kind="subtitles" srclang="en" label="English">

One practical note: browsers usually refuse to load a track from another domain unless it is served with the right CORS headers, so keep the VTT on the same site as the page when you can.

TXT: just the words

TXT drops the counters and the timing lines and keeps the caption text in order:

All right, so here we are, in front of the
elephants
the cool thing about these guys is that they
have really...
really really long trunks
and that's cool

Notice that a caption which was split over two lines on screen stays split here. That keeps the file faithful to the captions, but if you want flowing paragraphs you'll need to join lines yourself; the post on copying a transcript without timestamps shows a few ways to do it.

TXT is the right download for reading, searching, quoting, translating or pasting into an AI chat. It opens in any text editor or notes app. If you don't need a file at all, the RAW button shows the same text in a new browser tab so you can read or copy it straight away. More on this on the YouTube to text page.

Side by side

SRT VTT TXT
Timing kept Yes Yes No
Millisecond separator Comma Dot n/a
Header line None WEBVTT (required) None
Works with HTML5 <track> No Yes No
Video editors, desktop players Very widely supported Often supported No
Reading, notes, AI tools Works, but cluttered Works, but cluttered Best fit

Mistakes I'd watch for

Renaming instead of converting. Changing .srt to .vtt does not make a WebVTT file: the header is missing and the commas are still there. If you only have an SRT, either download the VTT version as well or add WEBVTT and a blank line at the top and change the comma to a dot in the timing lines only. A find-and-replace on every comma will also change commas in the dialogue.

Editing timing in TXT. Once the timestamps are gone, they can't be rebuilt from the text. If there is any chance you'll need the captions back on a video, keep the SRT too. Downloading both costs one extra click.

Expecting tidy blocks from auto-generated captions. Subtitles from YouTube's automatic captions follow YouTube's own segmentation, which tends to be short phrases that start and end mid-sentence, without much punctuation. For a professional edit, plan to merge some blocks and fix names. The post on how accurate auto-generated subtitles are goes into what usually needs fixing.

Odd characters in an older player. FetchSubs saves all three formats as UTF-8 text. Current players and editors handle that fine, but if accented letters or non-Latin scripts look garbled in an older program, set its subtitle encoding to UTF-8.
